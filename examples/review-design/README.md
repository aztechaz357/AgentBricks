# 見本: 設計書のレビューのスキル

`/new-skill` で作ったスキルの見本。材料はすべて架空。ここに置いてあるだけでは読み込まれない (有効なスキルではない)。

材料を置いてから、スキルができて試すまでの流れを、そのまま追えるように並べてある。

## 中身

| 場所 | 中身 |
|---|---|
| `inbox/` | new-skill に渡した材料。いつもの進め方のメモ (`memo.md`)、レビュー前の設計書 (`input/`)、指摘を受けて直した後の設計書 (`output/`) が 2 組 |
| `skill/` | できたスキル (下の「できたもの」) |
| `build-log.md` | new-skill の手順 1〜11 で、何を読み、何を決め、どの材料から何を取り出したかの記録 |
| `trials/` | new-skill の手順 8 で、作りながら試した 3 つの場面の入力と結果 |
| `check/` | できたあとに、別のエージェントが新しい設計書で試した結果 |

## できたもの

```
skill/
  SKILL.md                    手順 7 歩 (46 行)
  scripts/check_design.py     あいまいな言葉、章番号の飛びと重なり、要求番号の有無を、行番号付きで出す
  references/
    checklist.md              観点 10 個
    format.md                 指摘の一覧の型と、重要度の付け方
    notes.md                  用語集の場所、番号の形
    examples/                 材料の前と後 2 組と、試した場面
```

`assets/` は消した。会社の様式が材料になく、指摘の一覧は Markdown の表で足りるため。

## 作り方

### 1. 材料を置く

```
inbox/review-design/
  memo.md                     いつもの進め方
  input/01-receiving.md       レビュー前 (入荷登録)
  input/02-shortage-mail.md   レビュー前 (在庫不足の通知)
  output/01-receiving.md      指摘を受けて直した後 (同じファイル名)
  output/02-shortage-mail.md
```

メモには、表の列、重要度の付け方、用語集、要求番号のほかに、「あいまいな言葉を毎回同じ一覧で検索している」「章番号を毎回目で数えている」と書いた。毎回同じ答えになる作業はスクリプトにする、という判断の材料になる。

### 2. new-skill を呼ぶ

```
/new-skill review-design 設計書・仕様書のレビュー。レビュー前の設計書を入力に、指摘の一覧を出す
```

### 3. new-skill がしたこと

詳しくは `build-log.md`。要点は次のとおり。

| 手順 | したこと |
|---|---|
| 1 形を決める | 入力が確かめる資料、出力が指摘の一覧なので「確かめる」にした |
| 2 取り出す | 前と後の違いを、直した理由ごとに 20 か所挙げた。理由が同じものをまとめて観点 9 個にし、メモの「章番号」を 10 個目にした |
| 2 取り出す | 指摘の一覧の実物がないので、メモの表の列から型を作り、「例なしで作った」と書いた。重要度の付け方は型の「書き方の決まり」に入れた |
| 2 取り出す | メモのうち、あいまいな言葉の検索、章番号の数え、要求番号の有無の 3 つは、毎回同じ答えになるのでスクリプトにした。判断が要る観点は手順に残した |
| 3〜4 質問 | 7 つの質問を書き出した (置き場所、あいまいな言葉の一覧の残り、用語集の中身、番号の決まり、直した後の数値は誰が決めたか、など)。今回は聞けないので仮の答えを置いた |
| 6〜7 書く | 型を写し、`assets/` を消し、`run.py` を `check_design.py` に名前を変えた。SKILL.md は手順だけにして、参照の表に「手順 2 で実行する」「手順 3 で読む」と書いた |
| 8 試す | 下の 3 つの場面で試した |
| 9〜10 | 記録に 1 行足し、`python tools/sync.py` で検査した |

例: 前と後の違いが観点になったところ

| 前 → 後 | 観点 |
|---|---|
| 「速やかに完了」→「2 秒以内 (同時に 20 人)」、「少なくなった」→「発注点を下回った」 | 1 あいまいな言葉が数値や条件になっているか |
| 「見つからなければ E-101 を表示して終了」を追加、「0 件なら送らずに終了」を追加 | 2 異常時と境目の動きが決まっているか |
| 「2 と 3 は 1 つのトランザクション」を追加 | 8 途中で失敗したときにデータが食い違わないか |

### 4. 作りながら試した (new-skill の手順 8、`trials/`)

| 場面 | 結果 |
|---|---|
| 例の入力 (01 のレビュー前) | 指摘 11 件。前と後の違い 10 か所がすべて指摘に入った |
| 別の入力 (出荷指示の設計書。試し用に作ったもの) | 指摘 16 件。入れておいた問題をすべて拾った |
| うまくいかなさそうな入力 (空、見出しなし、ないパス、1,205 行) | スクリプトは前の 3 つで理由を出して止まり、大きい設計書でも全部拾った |

試して直したこと: Windows で止まったときの理由が文字化けしたので、スクリプトの標準エラーを UTF-8 にした。長い設計書で見落とさないよう、手順 3 に「章ごとに区切って当てる」を足した。1,205 行の入力は大きいので、ここには置いていない (スクリプトの結果だけ置いた)。

### 5. 別のエージェントで確かめた (`check/`)

作った本人とは別のエージェントに、スキルの手順書だけを渡し、見つけてほしい抜けを 9 個仕込んだ新しい設計書 (`check/03-shipping.md`) をレビューさせた。

| 仕込んだ抜け | 1 回目 | 直したあと |
|---|---|---|
| 「必要に応じて」 | 拾った (スクリプトも) | No 1 (スクリプトも) |
| 入力の形式と範囲がない | 拾った | No 5 |
| 在庫が足りないときの動きがない | 拾った | No 7 |
| 在庫と履歴を 1 つのトランザクションにしていない | 拾った | No 8 |
| 権限の前提がない | 拾った | No 9 |
| 「担当者」がどの担当者か分からない | 拾えなかった (用語集がないので、用語の観点ごと飛ばした) | No 2 (直したので拾えた) |
| 要求番号 (REQ) がない | 拾った (スクリプトも) | No 3 (スクリプトも) |
| 章番号 4 の抜け | 拾った (スクリプトも) | No 14 (スクリプトも) |
| 同時に登録したときの排他 | 観点の追加の候補として挙げた | 観点の追加の候補 |

1 回目で拾えなかったので、観点 6 と手順 4 を「用語集がなくても、人と物の呼び方が 1 つに決まっているか (どの担当者か) を見る」に直し、同じ設計書で試し直した。直したあとは 9 個とも拾えた。1 回目の結果は `check/03-shipping-review-1.md`、直したあとは `check/03-shipping-review-2.md`。

## 自分のリポジトリで使うには

`skill/` を `.github/skills/review-design/` に写し、`python tools/sync.py` を実行する。観点とあいまいな言葉の一覧は架空の設計書から作ったものなので、自分のレビューの前と後の資料で作り直すほうがよい。
