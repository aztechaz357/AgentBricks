# 積み上げの段階

部品は下から 1 個ずつ積む。次の段階に進むのは「進む合図」が出たときだけ。合図が出ないうちは、今の段階のまま使い込む。

| 段階 | 足すもの | 進む合図 (これが出たら次へ) |
|---|---|---|
| 1 | スキル 1 個。自分で `/<名前>` と呼んで使う | 実際の仕事で 3 回使い、手順を直すところがなくなった |
| 2 | スキルを足す (5 個くらいまで) | 1 つの会話で読むものが多すぎて、手順が混ざったり忘れられたりする |
| 3 | エージェント 1 個。スキルを 1〜3 個読ませる | 別の役割が要る。典型は「作った本人以外に確かめさせたい」 |
| 4 | エージェントを足す (作る役と確かめる役、など) | エージェントが 3 個を超え、どれを呼ぶか毎回迷う |
| 5 | 窓口 1 個。担当に割り振るスキル | 窓口が扱う仕事の種類が増えて、割り振りが混ざる |
| 6 | 窓口を分ける。共通の決まりをスキルに抜き出す | (ここまで来たら、自分の決まりを足していく) |

## エージェントを作る理由

スキルのままで済むなら、エージェントにしない。エージェントにするのは次のどれかが当てはまるときだけ。

- **文脈を分けたい**: たくさん読む作業で、本来の会話を汚したくない。
- **独立して確かめたい**: 作った本人の思い込みを持ち込まずに見直させたい。
- **道具を絞りたい**: 読むだけ、編集はしない、などを仕組みで守らせたい。

## 窓口がスキルである理由

割り振り役は、利用者に確かめたり結果を伝えたりしながら進めるので、利用者との会話の中で動くスキルにする。エージェントにすると、会話から切り離された所で動き、途中の様子が見えにくくなる。

Claude Code も Copilot も、エージェントからほかのエージェントを呼ぶ仕組みはある。それでも、階層を深くすると何がどこで動いたか追いにくくなるので、ここでは「窓口 (スキル) → エージェント」の 1 段だけにする。

## 崩れないための決まり

- 1 回に足す部品は 1 個。足したら使ってみてから次を足す。
- 1 スキル = 1 作業。SKILL.md が 60 行を超えたら、型や観点や知識を references に移すか、スキルを分ける (`tools/sync.py` が止める)。
- エージェントが読むスキルは 3 個まで。
- 同じ文が 3 つ以上のスキルに出てきたら、共通のスキルに抜き出す。
- 使っていない部品は消す。`docs/organization.md` の「どこからも読まれていないスキル」を時々見る。
- 足した理由と消した理由は `docs/journal.md` に 1 行ずつ残す。
